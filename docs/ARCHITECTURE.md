# Architecture

SoundWaive is a native Android application with one Kotlin app module and a Rust analysis crate. There is no server, web runtime, account system or Internet permission.

## Music to video

1. Android's document picker returns the selected audio URI. `AudioEngine.kt` decodes it with `MediaExtractor`/`MediaCodec`, retains the PCM needed for export, and creates a mono 11025 Hz stream for analysis (`MonoDownsampler.kt` averages input frames, so content above 5.5 kHz does not alias).
2. The Rust engine computes FFT frequency bands, energy envelopes, transients, tempo, beats and approximate bass pitches. Tempo comes from a harmonic autocorrelation comb (cubic interpolation, sub-step refinement, log-normal prior around 120 BPM), then an octave check that doubles a half-time reading only when attacks fall between the slow beats (and halves only when every other beat is weak). JNI returns the result of writing a versioned `CPULSE01` analysis file.
   - `engine/src/lib.rs` orchestrates per-frame analysis (hop 256 samples, 43.07 frames/s; frame `f` is centred on time `f * 256 / 11025`). A 2048-sample window serves bands and bass pitch.
   - `engine/src/onset.rs` runs a 512-sample window on the same grid: positive spectral flux in a bass band (linear magnitude), a body band and an air band (log magnitude with a neighbouring-bin maximum filter). Offline peak picking uses a local-mean and ~1 s median threshold, parabolic sub-frame timing and measured latency correction. Hits become the kick/snare/hat envelopes (0.15 s decay) and the onset list.
   - `engine/src/beat.rs` estimates tempo by fractional-lag autocorrelation with a harmonic comb and a log-normal prior around 120 BPM, tracks beats by dynamic programming (Ellis 2007), snaps beats to nearby onsets and picks the downbeat phase from bass attacks and beat-synchronous bass-register change.
   - Analysis file: `CPULSE01`, six header floats, the frame table, notes, onsets, then an optional `SWBEAT01` section (u32 count, then time/strength/downbeat floats per beat). Readers that predate it stop after the onsets.
3. `Models.kt` validates analysis/settings data. `MainActivity.kt` coordinates playback, controls, saved looks, lifecycle, cancellation and file destinations. Since 1.14.0, export is handed to `ExportService`, a foreground service (`mediaProcessing` on API 35+, `dataSync` on API 29–34 and the original foreground API on 26–28), and `ExportSession` holds the progress so the activity can reattach. Since 1.15.0, a Release Pack job runs seven renders in that same service: `ReleasePlan.kt` (pure, unit-tested) picks the song windows from the existing analysis, `ReleasePack.kt` turns each into a per-clip look and `VideoExporter.Options` and saves the result to Movies through MediaStore (see [RELEASE-PACK.md](RELEASE-PACK.md)).
4. Backgrounds (`BackgroundMedia.kt`, `BackgroundMath.kt`) are the renderer's bottom layer in the same pass, so dimming, beat reactions, grain, glow, vignette and fades apply to them. Every source maps music time to a frame (loop or hold): photos are scaled once; GIFs render through `Movie.setTime`; videos decode in order (MediaExtractor/MediaCodec to a SurfaceTexture, a GLES pass into a working-size pbuffer, `glReadPixels` into reused bitmaps) on a private thread with its own EGL context. Export opens a private blocking instance at the Render quality size; the preview uses a non-blocking 360p instance. Since 1.12.0 a GPU export switches the decoder (`MediaCodec.setOutputSurface`) to an external texture of the export's own GL context and samples it in the shader pass (zero copy); the read-back is only used by the preview and the Canvas fallback.
5. `VisualRenderer.kt` draws a deterministic composition from music time, settings and seed. The same renderer powers preview and export, including custom artwork, crown textures, musical staves, particles and layers. Beat effects (`BeatFx.kt`, pure timing and easing rules with JVM tests) read the tracked beat grid from the analysis as primitive arrays, so per-frame lookups are binary searches with no allocation; a tempo override or an analysis without a grid uses a fixed 4/4 grid from 0 s.
5b. `AiUpscale.kt` (1.13.0) sharpens and cleans small background photos (once, cached in files/) and export video frames (cached per frame in cache/ai-video/) with Real-ESRGAN-General-x4v3 through LiteRT `CompiledModel`, on a compatible Tensor G5 when its AOT model is bundled, then the GPU or CPU. The 32-bit Intel backend uses the LiteRT C interpreter and checks for SSE4.1. See `docs/AI-UPSCALE.md`.
6. `VideoExporter.kt` draws each frame with a hardware-accelerated Canvas (`Surface.lockHardwareCanvas`) into a SurfaceTexture at the Render quality working size; the encoder's GLES pass samples that external texture (bilinear upscale) and stamps the exact presentation time, so no CPU bitmap or per-frame texture upload is involved. If the GPU path cannot start or fails, the remaining frames use the previous CPU bitmap path. Since 1.12.0, on Android 10+ with OpenGL ES 3 the scene is recorded into a `RenderNode` and rendered by a non-opaque `HardwareRenderer` instead, and `GpuFx.kt`'s single GLES 3.0 shader pass adds the background color, video background, paper grain, build-up darkening, drop flash, grain specks, vignette, titles and fades from a `PostFx` filled by `VisualRenderer.draw` (in the Canvas order, with Paint-rounded alphas). Any setup failure keeps the 1.3.0 Canvas path. Audio is encoded as AAC. Device encoders constrained to landscape can use a rotated frame plus MP4 orientation metadata. The exporter tries other supported encoders, then lower frame rates or resolutions, and reports any settings change.
7. `Mp4AudioTiming.kt` adjusts MP4 audio edits to remove AAC encoder priming while retaining the full audible tail. The reference encoders use their verified 2048-sample delay. Other compatible AAC-LC encoders are calibrated with a separate band-limited pulse before export. Media-data offsets remain unchanged. JVM fixtures and native re-import measurements cover this behavior.

## Compatibility

The product name is SoundWaive. The existing package/JNI namespace, settings format and analysis signature deliberately remain compatible with the original CrownPulse build. Changes to binary formats need explicit version handling and migration.

## Storage and lifecycle

Imported music and generated analysis stay in app-local storage. Export uses a user-selected URI. A fresh app launch returns to the bundled generated demo; saved looks and imported artwork persist. If an export is still running, a relaunch keeps that song and shows the current progress. Analysis still runs off the UI thread and needs the app to stay open. Export runs in `ExportService` (foreground type `mediaProcessing`) so Android will not freeze the process when the app is no longer on screen; a progress notification shows the percentage and a cancel action. A partial wake lock is held for the same 6-hour window as that service type, so the CPU can keep working with the screen off. Cancellation cleans incomplete output. Audio focus and headphone disconnection pause playback.

## Testing boundaries

Host Rust tests cover FFT, normalization, onset timing, adaptive thresholds, tempo resolution, beat phase, downbeats, silence/short input and analysis serialization. JVM tests cover MP4 timing metadata, analysis-format compatibility, downsampling and non-destructive failure cases. `tools/eval_sync.py` measures onset, kick/snare envelope, tempo, beat and downbeat accuracy on synthetic songs with exact ground truth, including held-out songs not used for tuning. Android lint and real native compilation cover the Android surface. Optional emulator instrumentation exercises decoding, JNI, rendering, export and artwork import using private fixtures.

Numerical beat and pitch estimates are intended for animation. Do not present them as guaranteed transcription. Physical-device codec support, thermal behavior, export speed and long-running memory use need measurement on representative phones.
